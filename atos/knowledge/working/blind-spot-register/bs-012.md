## What could fail?

`handle_new_user` creates `profiles` only — not `living_profiles`. Persistence depends on first `GET /api/living-profile` or practice-route ensure. Onboarding (`completeOnboardingAction`) also does not create LP.

If ensure fails (missing `profiles` row / FK, RLS, table unavailable), ContinuityHome soft-fails and practice returns `readiness_unavailable` with a bare redirect to `/app` and no reason. Orphans are only detected when someone runs `practice-readiness:check:live` (not in default CI).

## Unintended consequences

- Production can accumulate orphan accounts again between signups and first ensure.
- Profile PUT races (`expectedVersion` 0 vs ensure-created 1) produce 409 with weak UI recovery.
- “Read” paths perform writes (harder to audit; concurrent mutation risk).

## Trust impact

Medium. Intermittent “Begin does nothing” / stuck home returns if ensure fails silently.

## Autonomy impact

Low.

## Complexity impact

Medium. Two creation paths (trigger vs lazy ensure) diverge over time.

## Mission alignment

Identity SSOT should be complete when a member exists, not when they happen to hit ContinuityHome.

## Mitigation / decision

Mitigating 2026-08-05: migration `20260805_living_profile_on_signup.sql` creates `living_profiles` inside `handle_new_user`; onboarding writes purpose; ensure remains backup; profile UI refreshes on 409. Residual: practice redirect still omits reason string.
